# RB-Y1 Control UI and IDE-authored Tasks

A Qt frontend and a separate robot-facing backend node for operating the RB-Y1
MuJoCo robot through ROS 2. It supports the mobile base, manual joint/TCP moves,
and a small Scenario system whose Tasks are edited in Python rather than in the
UI.

## Node and topic architecture

The ROS mode is split into two processes:

```text
/rby1/rby1_control_ui
  -> /rby1/control/command  (std_msgs/String)
  -> /rby1/rby1_control_backend
  -> RB-Y1 driver topics, services, and actions

/rby1/rby1_control_backend
  -> /rby1/control/state    (std_msgs/String)
  -> /rby1/control/event    (std_msgs/String)
  -> /rby1/control/response (std_msgs/String)
  -> /rby1/rby1_control_ui
```

`control/command` is the planner-facing interface. Messages use the versioned
JSON envelope implemented in `topic_protocol.py`:

```json
{
  "schema_version": 1,
  "kind": "command",
  "source": "dynamic_planner",
  "request_id": "optional-unique-id",
  "operation": "set_velocity",
  "arguments": {"vx": 0.15, "vy": 0.0, "wz": 0.0}
}
```

Supported operations are `set_velocity`, `stop`, `prepare_robot`,
`request_power`, `request_servo`, `request_stream`,
`request_control_manager`, `request_cartesian_snapshot`, `jog_joint`,
`move_joint_group`, `jog_cartesian`, `move_cartesian`,
`cancel_active_motion`, `cancel_motion`, `start_task_command`,
`cancel_task_command`, and `shutdown_safely`. Robot-facing validation remains
inside the backend node; publishing a command does not bypass its state, joint
limit, collision, or action-conflict checks.

When `request_id` is non-empty, `control/response` reports whether the backend
accepted the transport request. Motion completion is reported asynchronously
through `control/state` (`task_commands`) and `control/event`; a transport
acceptance is not a claim that the robot has completed the motion. Until a
planner-level ownership policy is added, only one controller should publish
motion commands at a time.

The normal launch file starts both nodes. They can also be run separately when
developing a planner:

```bash
ros2 run rby1_control_ui control_backend --ros-args --params-file <config.yaml>
ros2 run rby1_control_ui control_ui --ros-args --params-file <config.yaml>
```

The base path reuses the communication structure of
`12_mobile_base_control.py`:

- `geometry_msgs/msg/Twist` publisher on `cmd_vel`
- optional `robot_power`, `robot_servo`, and `stream_control` service clients
- optional `robot_state` subscriber
- continuous 25 Hz command publication

The visual interaction follows the supplied MuJoCo Qt example:
buttons and keyboard events start motion while held and publish STOP when released.

## Scenario workflow

The Scenario tab intentionally contains only:

- a Task List with Reload, Run, and Delete;
- Emergency Stop;
- Get Q and Get TCP with a clipboard Copy button;
- a read-only preview of the selected Task.

Edit `rby1_control_ui/task.py` in the IDE. With a ROS workspace, build using
`colcon build --symlink-install` so the UI imports that editable source, then
press **Reload Tasks**. A validated, single JSON catalog is written atomically
to `${XDG_CONFIG_HOME:-~/.config}/rby1_control_ui/task_catalog.json`. Set
`RBY1_TASK_CATALOG` to override that path. Deleting in the UI removes the
compiled catalog entry; Reload restores entries still registered in `task.py`.

Get Q returns joint angles in degrees. Get TCP returns base-frame
`[x, y, z, roll, pitch, yaw]`, with metres for translation and degrees for
orientation. These strings can be copied directly into `task.py`.

Before authoring a Cartesian Task, establish a repeatable, non-singular body
posture. The included `ready_pose` moves the torso and both arms together to
the RB-Y1 SDK Cartesian-ready posture. Its optional pre-control stage remains
commented out in `task.py`. Run `ready_pose`, use Get TCP after it finishes,
paste that fresh pose into `right_tcp_example`, and then press **Reload Tasks**.
Task Cartesian motion is generated by the SDK `CartesianCommandBuilder`; the
driver rejects malformed commands or an unsafe starting state and monitors
live joint limits and collision distance throughout execution. A nearly
straight arm can still make Cartesian tracking unreliable, so a repeatable
non-singular starting pose remains important.

`joint_absolute_multi()` sends two or more body groups in one ROS action goal;
it is simultaneous rather than the sequential behavior produced by separate
Task lines. `whole_body_joint_absolute()` is the torso-plus-both-arms convenience
form used by `ready_pose`. For example, a simultaneous two-arm command is:

```python
joint_motion = [5.0, 0.2, 0.2]
task.joint_absolute_multi(
    {
        "right_arm": right_q,
        "left_arm": left_q,
    },
    joint_motion,
)
```

```python
from .task_commands import Task, list_sum


def tool_approach():
    task = Task("tool_approach")
    pos = [0.35, -0.25, 0.85, 0.0, 0.0, 0.0]
    tcp_motion = [2.0, 0.05, 0.20, 0.20]
    task.linear_absolute(
        "right_arm", list_sum(pos, [0.0, 0.0, 0.03, 0.0, 0.0, 0.0]), tcp_motion
    )
    task.delay(750)  # milliseconds
    return task
```

The four-value `tcp_motion` list is ordered as `minimum_time` (s),
`linear_velocity` (m/s), `angular_velocity` (rad/s), and
`acceleration_scaling` (0.0–1.0). The example values are conservative starting
points, not universal labels such as “slow” or “fast”; the safe result also
depends on the pose, payload, environment, and robot configuration. Joint
commands use the three-value `joint_motion` list ordered as `minimum_time` (s),
`velocity_limit` (rad/s), and `acceleration_limit` (rad/s²). Task execution
rejects values above the verified RB-Y1 M v1.3 model limits; head Task motion is
blocked because that model does not provide a verified head acceleration limit.

Tasks can be joined without copying their command bodies:

```python
combined = Task("combined")
combined.extend(tool_approach())
combined.extend(tool_approach())
```

Only functions returned by `build_tasks()` appear in the UI. A running Task is
executed one command at a time by a Qt timer; there are no blocking sleeps.
Base and manual Joint controls are disabled during execution. Every step checks
fresh robot state, EMO/collision state, control state, command timeout, and the
driver result. Relative Q/TCP commands additionally require fresh, verified
source state. Emergency Stop clears base velocity and calls the driver's common
motion-cancel service.

## Object-pose interface

Camera and mock-perception producers use the same typed ROS boundary:

- relative topic: `perception/object_pose` (normally
  `/rby1/perception/object_pose`);
- message type: `rby1_msgs/msg/DetectedObjectPose`;
- one message represents one valid object observation;
- `header.stamp` is the image capture/detection time;
- `header.frame_id` is the source frame of `pose`;
- position uses metres and orientation uses a normalized ROS quaternion in
  x/y/z/w field order;
- `object_id` is a nonempty, stable producer-assigned identifier;
- `confidence` is in the inclusive range 0.0 through 1.0.

A producer does not publish a zero pose to mean "not detected". Consumers treat
missing or stale observations as unavailable. The configured consumer target
frame is `base`; conversion into that frame will be performed by the future
frontend `CameraClient`, not by the producer. Real and mock producers must use
this identical contract so Task execution does not depend on the source.

## Intended workspace location

Place this package at exactly:

```text
<rby1_ros2_ws>/src/rby1-ros2/rby1_control_ui/
```

Do not place it inside `rby1_examples/rby1_examples/`. It is deliberately an
independent ROS 2 package so the vendor/example package does not need to be edited.

## Key mapping

- Up or W: forward
- Down or S: backward
- Left or A: lateral left by default
- Right or D: lateral right by default
- Q / E: rotate counterclockwise / clockwise
- Space or Escape: stop

The arrow-key mode can be changed in the UI so Left/Right rotate instead of strafe.

## Run without ROS

```bash
RBY1_UI_BACKEND=mock ros2 run rby1_control_ui control_ui
```

In Mock mode, press Prepare Robot before running a Task. Mock moves complete
immediately and are intended for UI/sequence verification only.

## Qt dependency

The code supports either PySide6 or PyQt5. Only one is required at runtime.
Installation and run verification should be performed after the package files are
placed in the workspace.

## Safe file-copy helper

After extracting the downloaded ZIP, the package can be copied without editing the
existing vendor packages:

```bash
bash /path/to/rby1_control_ui/install_into_workspace.sh /path/to/rby1_ros2_ws
```

The script checks for `src/rby1-ros2`, refuses to overwrite an existing package,
and performs no build or UI execution.
